# Mushroom planner

React + TypeScript with MUI. Run `npm start` for the local app. OCR runs locally; `prestart` and `prebuild` copy its bundled assets into `public/ocr`.

Run `npx tsc --noEmit`, `npm run lint`, `CI=true npm test -- --watchAll=false --runInBand`, and `npm run build` before shipping.

`View` owns Calculator/Planner navigation and their shared card. Desktop tabs sit inside that surface; mobile retains bottom navigation. The tool panels use their embedded presentation in View, with standalone cards available to other callers. `MushCalcRadio` and `ExistingMushroomCalc` are the active calculators; `JoinPlanner` is their always-visible additional-player section. `MushroomPlanner` owns saved records, projection views and Undo. `PlannerFinishEditor` owns mushroom entry; `DailyTries` shows free-try accounting.

The numeric field no longer has unused stepper or hidden-label modes, and countdown fields no longer expose unused focus callbacks.

`NumberSpinner`, `CountdownFields`, `SimpleDateTimeInput`, `MushroomTypeField`, `formStyles` and `theme` share form behavior. Pickers use MUI’s default appearance, device detection and accessible section-based fields; keep only domain validation, limits and time shortcuts in their wrappers. `SectionAccordion` uses MUI’s default surface/disclosure styling and shares unique summary/panel IDs and heading levels across Settings and screenshot review. `useScreenshotReader` owns cancellable local OCR queues; the two upload surfaces decide whether results autofill immediately or remain drafts.

`useTabScrollRestoration` shares scroll capture and restoration across mobile tool navigation and the planner’s Stages/End times tabs. Each planner view remembers its own position. On desktop and mobile, the first Stages visit shows the current projected stage (the first unfinished step's stage); End times starts at today's date heading, or the top if today has no mushrooms. Card and page positions are kept separately, and month/timezone/date changes initialize the new context.

`ResponsiveDialog` shares the manual-editor and screenshot-review dialog shell. `plannerDateTime` shares compact planner timestamps while leaving date-only headings and calculator-local clocks separate.

Feedback stays quiet: calculator validation/read/copy failures are persistent inline errors. Successful copies show a brief “Copied” snackbar. Planner pop-ups are limited to saved changes with Undo and are hidden when the planner is inactive; import/read/save errors stay inline. There is no background update notification. `ActionFeedback` provides copy confirmations and the planner Undo snackbar with a five-second timeout that pauses during focus/hover. `AppNotice` is reserved for inline screenshot-review warnings.

`stagePlanner` holds allocation and storage validation. `plannerRecords` identifies matching battles. `hypotheticalTries` resolves the automatic month and planned free starts; `plannerTiming` flags task-transition risks. Date/time inputs for the selected planner timezone use `WallClockProvider` and explicit IANA clock resolution. Calculator dates use browser-local Dayjs; keep those meanings distinct.

Records are saved locally under `pikmin-bloom:stage-planner:v1`; JSON export/import is available in Planner settings. Import combines mushrooms using shared IDs and running name/type identity, takes incoming entries as the latest updates, and keeps this device’s settings. It never removes unrelated records; Undo reverses the import. New and invalid stores are empty. Sample data exists only in `src/testFixtures` and is not imported by production code. Keep tests that need examples explicitly seeded.

`PlannedTryFields` provides optional titles and planned end/start-date fields in the mushroom editor. The planner heading scrolls away on desktop and mobile; the compact view controls stay pinned. Add mushrooms stays in the desktop toolbar and uses a floating button on mobile. The sticky planner toolbar opens Daily tries in an anchored desktop popover or mobile bottom sheet, keeping the schedule scroll position. Daily tries shows date-by-date free-try accounting without a second entry form; new planned mushrooms use Add mushrooms → Add manually → Planned. Stages and End times show one row per mushroom, ordered by end time, with any calculated start beneath that mushroom. Starts never count toward stage quotas.

`usePlannerState` and `plannerPersistence` merge only changed records/settings with the latest saved plan and reconcile browser storage events. Independent edits and deletions survive cross-tab saves; concurrent edits to the same mushroom use the arriving change. Undo reverses the local record change while retaining unrelated later changes. Unsaved edits stay in memory if storage fails. Settings retains a critical save-failure alert with Retry save and Export controls; retry merges pending changes with the latest saved plan.

Settings groups Plan, Timing warnings and Device & backup using consistent headings and dividers. Event progress fields are directly visible whenever Settings is expanded, without an additional disclosure. Valid edits save immediately and store an `asOf` time for that event month. Unchanged numeric focus/blur never moves that time or resets the credited count. Only later ends advance from this point; earlier ends remain editable in End times. Reset restores the full allocation. Import combines records while keeping the receiving device's event progress and other settings.

Canceling a start-time calculation restores the mushroom editor draft without saving it.

The running-battle update note appears once below the planner heading. `PlannerTimeField` uses the same responsive MUI picker configuration as other date/time controls, storing recurring sleep clocks as HH:mm without interpreting them on the browser's current daylight-saving date.

`plannerTiming` checks every mushroom against the previous mushroom task's final end time: the player must claim that task's reward before the next task can count mushrooms. The minimum gap uses full elapsed time, and sleep is a separate check for no awake opportunity to claim before an ending. Waking at 10:00 before a 10:18 ending is safe when the preceding task ended at 01:21, even with a 30-minute minimum; the elapsed gap is 8 hours 57 minutes. All endings inside a risky window are flagged, including multiple mushrooms assigned to the same task; ordinary clustering after the window is safe. An unset minimum appears empty and stays empty when cleared/reloaded, while the stored numeric zero retains its disabled meaning for compatibility. Simultaneous endings across task boundaries are risky even without a minimum gap. The event month and optional saved progress supply the starting boundary: opening tasks begin at local month start, and pending tasks/filled quotas use the saved progress cutoff. An already unlocked partial mushroom quota needs no initial claim. Warnings never alter allocation.

`numericInput` parses the same locale-specific digits and separators it formats. Editable number fields remove grouping while focused and restore it on blur, so changing one digit cannot leave an invalid thousands group. Localized decimal separators and invalid drafts are preserved; read-only values stay grouped. Calculated metadata is invalidated when a planned mushroom's type changes; missing calculator inputs clear the selected output. Daily start dates extend from at least today and can collapse after expansion.

The small footer shows a single numeric build version. `npm start` and `npm run build` generate it when the process starts, so a new build can be identified without displaying commit or date details.

The screenshot-review loading bar measures files processed in the current batch, alongside a live count needing review. This includes failed reads and drafts with missing or invalid required values, excludes files still waiting to be read, and decreases as problems are corrected. A failed read counts as processed and retains its review warning. The active file is not processed until its attempt finishes; changing OCR phases does not advance the bar. Each upload or retry starts its own batch, and percentage changes animate smoothly unless reduced motion is requested.

Screenshot review retains failed and unread files with their original preview, filename, reading stage and error. Each can be retried individually, skipped, or converted to an editable manual draft; saving successful drafts keeps remaining failures open. Unresolved screenshots show warning icons on collapsed headings and on Add mushrooms / Resume screenshots; the icons and obsolete reading warnings clear when all required values are valid. Successful and failed reads both offer an optional View screenshot dialog with a larger original image and an Open full size link. Closing the preview preserves form edits. The calculator retains its selected original after successful reading, until replaced or cleared. Review drafts and original files survive closing/reopening the dialog during the session, but do not survive a page reload. Completed battles can be imported into the planner using capture time plus countdown. The calculator presents a past projected finish as information and offers calculation from capture time, explicitly labeled, rather than requiring a newer screenshot. Missing capture metadata still requires manual entry; elapsed time is never guessed.

“Exclude from stages” keeps the mushroom and its free-try accounting while removing it from stage allocation. Excluded rows show “Excluded from stages”; use Edit and uncheck “Exclude from stages” to restore allocation. Remove deletes the record. The stored `missed` field is unchanged for saved-plan compatibility.

Copy actions use text buttons. A failed copy leaves a selectable timestamp beside the button after its temporary snackbar closes; a successful copy clears that fallback.


Uploaded mushrooms accept an optional Start date in screenshot review and in Edit, using the same date field as planned tries. Explicit dates count toward daily free tries; unknown starts do not. Screenshot updates preserve an existing start date unless explicitly changed or cleared. A reupload for the same running name/type updates that record and clears stage exclusion without duplication. Ticket-funded and excluded records retain their existing accounting semantics.

Title OCR uses one calibrated layout in `screenshotImage`: locate the navigation chevron using a small template, infer the horizontally centered bubble from its fixed padding, and crop its label area. Coordinates scale with screenshot width, and the anchor can move within the upper quarter of the screen. Tesseract receives the original cropped pixels. There is no capsule-boundary fitting, title component filtering, flood-fill cleanup, broad-strip fallback, or punctuation stripping. Missing anchors use normal manual title entry in screenshot review.

All seven supplied screenshots read their titles exactly with this crop, including Heide, Montour and the German title. Layout tests also exercise rescaled screens, different aspect ratios, shifted anchors, shorter labels and preserved accents/punctuation. These samples share one phone format; the width-scaled, centered layout remains an assumption to verify on other devices.

Expected battle screenshots have a scene above a white details card, approximately dividing the screen in half. A blurred bubble near the top contains the location name; large centered text near the top of the card gives the mushroom type. Immediately above the card, HP is red on the left with a pie icon of variable fill, and its white countdown is below it. AP is on the right beside the two-figure icon (to the left of the digits in the supplied images). One through four stars correspond to green, yellow, orange, and deep orange with a blue surrounding effect. The reader matches the common figure contours and samples their fill instead of inferring a number from star count. HP currently reaches roughly 2.8 million; that is context, not an acceptance ceiling or a rule for reconstructing missing digits.

Numeric screenshot reading uses the health circle's white rim and the common white contours of the strength figures to anchor the number fields. The pie's interior fill and the strength icon's changing star decorations are ignored. AP icon matching is independent of fill hue; after locating it, the reader samples the figures' current fill. HP retains its fixed red classification. Number and countdown crops follow icon spacing; the white panel limits the search area.

`readBattleNumber` reads HP and AP directly using one game-font model in `battleNumberFont.json`: the ten digit shapes and comma, plus their character advances. The glyph samples come from three HP screenshots (IMG_3632, IMG_4084, IMG_4095), and apply to both HP and AP in all four color styles. It compares original fill and adjacent white-contour pixels without modifying the source, with a small alignment tolerance. There is no flood-fill cleanup, stroke erosion, component deletion, digit substitution, or fallback to generic OCR for these fields. Recognition must start beside the icon, follow consecutive character cells, satisfy numeric grouping, and beat competing digit and whole-number matches. Unreadable remaining ink/contours block a shorter HP result; AP must reach its expected right alignment. Font agreement scores are heuristics, not correctness probabilities. Ambiguous/incomplete matches require manual entry. There is no hard seven-digit or 2.8-million ceiling.

Tesseract still reads the countdown and optional identity fields. The countdown's white text is isolated as one row, excluding detached health-comma outlines; soft edges remain gray. Every countdown value needs a recognized unit label in descending order, including four-number readings. English labels and the existing German abbreviations are supported; arbitrary four-number strings are rejected. Insufficient countdown digit-confidence evidence leaves it blank. Tests use independent native pixels covering all ten digits from three other screenshots, new number sequences, changed colors/pie fills/stars, missing cells, damaged outlines, empty backgrounds, vertical shifts, and unrelated artwork. The damaged-outline IMG_4180 case retains and reads its final 1.

The 39 original screenshot readings are manually transcribed in `src/testFixtures/battleScreenshotReadings.json`. On macOS, run `node scripts/check-battle-screenshots.cjs <screenshot-directory> --report <report.json>` to compare the icon crops, OCR, and parsers against every health, AP, and countdown value at original resolution. Add `--allow-rejections` to permit fields that explicitly require manual entry; incorrect accepted numbers still fail. Rejections are reported separately and never count as exact matches. This check requires the original files and installed OCR data; it does not depend on names or resized variants and does not exercise browser canvas resampling. These examples were used during development, so they are a regression set, not an independent accuracy estimate.

Mobile keyboard handling is passive: `useMobileKeyboard` listens only for viewport resizing to reserve bottom space and hide fixed controls. Native browser focus scrolling owns input visibility; do not add scroll calls, focus-settling timers, or visual-viewport pan handlers. Dialogs and autocomplete popups use MUI's default placement. Preset mushroom searches set `clearOnBlur={false}` so a focus interruption does not discard partial text. Keyboard regression tests simulate viewport events; a desktop phone-size viewport does not verify an actual iOS software keyboard.

Additional players is a normal, always-visible section with the complete form. Bullhorn time, the timing slider, additional AP and player controls remain mounted and disabled until the desired finish is valid; invalid values disable controls in place. Copy icons sit beside their time fields, with failures underneath. Keep native focus scrolling; typing never triggers app-driven scrolling.
