# Mushroom planner comparison

Research snapshot: October 30, 2026. Event progress and combining plans from two devices have since been implemented. Finding an individual battle by name is the main remaining useful gap. The current app already covers the main carryover-planning workflow; copying every timer-management control would add scope with less benefit.

This is research only. I inspected current source and test assertions, without changing production code or executing tests. Reference features come from the saved [production-site audit](mushroom-timer-feature-audit.md), which records direct inspection of SoftSpot's controls and help. A fresh [first-party page read](https://softspot.nl/pikmin/mushroomtimers/) independently exposed its title-search input, but its JavaScript-only help and panels were not readable through that interface; those details remain audit evidence, not newly verified controls. Usability comparisons below are reasoned judgments, not measured user results.

## Useful gaps, in order

1. **Set existing event progress, including partial quota — implemented.** Settings shows Stage, Step and Mushrooms already counted directly. Valid edits save immediately with a starting time for that month; unchanged focus/blur does not move it. Earlier ends stay editable in End times, while only later ends fill the remaining quota and later tasks. Reset restores full allocation. The template still repeats beyond stage 4 only when needed. [Progress UI](../src/EventProgressSettings.tsx), [allocation and validation](../src/stagePlanner.ts), [integration tests](../src/MushroomPlanner.test.tsx).

2. **Find a battle by title — high value for a batch of 34.** The current End times view helps when the date is known, but neither view has title search; manual title entry also lacks saved-title suggestions. SoftSpot exposes title search directly and the audit records saved titles. A simple title filter that preserves a route back to the full projection would reduce scanning when someone joins and changes a battle's end. Suggestions could come from existing records without adding a title registry. Keep matching semantics visible: current normalized title + type identifies one actual battle, while hypothetical entries remain distinct. Search must not change allocation or turn hidden results into an incomplete-looking quota. Evidence: [complete planner view](../src/MushroomPlanner.tsx#L97-L137), [title field](../src/PlannerFinishEditor.tsx#L58-L59), [identity rules](../src/plannerRecords.ts#L3-L16), [reference title-search input](https://softspot.nl/pikmin/mushroomtimers/), [saved-title audit](mushroom-timer-feature-audit.md).

3. **Device-plan combining — implemented after this review.** Import now combines mushrooms with the current plan. Saved IDs update shared records, including renamed or edited planned tries; running battles also deduplicate by normalized name and type. Independently planned tries remain separate. Incoming entries are authoritative regardless of capture age, all imported capture/start/ticket/missed metadata is retained, and the existing device's month/timezone/sleep/minimum-gap settings stay in place. Undo restores the pre-import records. There is one import behavior, with no replacement option or conflict-selection workflow. This supplies the reference's useful file-merge outcome; clipboard transfer remains absent. Evidence: [merge policy](../src/plannerRecords.ts), [import wiring and Undo](../src/MushroomPlanner.tsx), [merge tests](../src/plannerRecords.test.ts), [integration test](../src/MushroomPlanner.test.tsx), [reference transfer audit](mushroom-timer-feature-audit.md).


**Lower priority:** optional duplication of a *planned* try could reduce repeated input; the current daily form already retains its values after Add, so this is not a glaring gap. Reversible cleanup of old ended records may eventually help, but bulk deletion should not erase active-month historical ends needed for projection. Custom labels, participation markers and CSV are useful only if a concrete organizing/sharing need emerges. Evidence: [retained daily form](../src/DailyTries.tsx#L18-L28), [single-record removal](../src/MushroomPlanner.tsx#L135-L137), [allocation depends on saved ends](../src/stagePlanner.ts#L72-L87), [reference priorities 9–13](mushroom-timer-feature-audit.md).

## Usability advantages and limits

**Where the reference has an advantage:** its searched title list provides a direct route to a known battle; its adjustable starting point handles users without a full event history; its merge controls serve two independently edited device copies, an outcome the current app now also supports. Compact totals and duplication may also reduce navigation/input for some users, but their practical benefit has not been tested with a populated schedule. The reference's icon-tabbed gear panel hides much of this capability, so its control layout is not automatically the preferable design. [Reference controls and untested cases](mushroom-timer-feature-audit.md#less-obvious-controls-and-limitations).

**Where the current planner has an advantage for the stated workflow:** Stages and End times are labeled top-level views; non-mushroom tasks remain visible between quotas; dated end groups and secondary start annotations connect a plan to actual timestamps. The bottom daily planner counts known planned free starts on their start day, permits 4/3, excludes mushroom tickets, and offers reversible clearing. A daily start allowance is not used as a cap on ends. Sleep/minimum-gap warnings apply at task transitions and do not silently discard allocations. These affordances directly support carryover planning; their usability is inferred from the controls and behavior, not a timed comparison. [Views](../src/MushroomPlanner.tsx#L103-L131), [start accounting](../src/hypotheticalTries.ts#L18-L25), [4/3 test](../src/MushroomPlanner.test.tsx#L49-L64), [ticket exclusion](../src/plannerPreferences.test.ts#L24-L29), [transition logic](../src/plannerTiming.ts#L29-L39).

**Intentional boundaries:** time passing implies completion; users correct ends, mark Missed, or remove records themselves. All non-missed ends allocate even when close together or during sleep. The automatic month is the earliest saved end month, never earlier than the current month; an empty plan starts next month, with override in Settings. Selected IANA timezone handling includes nonexistent/repeated DST clocks. Readiness gates, forced completion, a live countdown, example records, an all-month archive and exact-second display are not gaps to pursue. Historical recommendations in the audit should be read in light of these later product decisions. [Completion/allocation](../src/stagePlanner.ts#L72-L87), [Missed](../src/PlannerFinishEditor.tsx#L73), [month defaults](../src/hypotheticalTries.ts#L9-L16), [month override](../src/PlannerSettings.tsx#L29-L33), [DST assertions](../src/stagePlanner.test.ts#L56-L81).

The final source recheck confirmed the mushroom-ticket wording, accessible sleep-settings explanation and numeric OCR-confidence warnings; these are completed polish, not backlog items. The confidence check applies to health/AP/countdown OCR, while identity fields retain missing/unreadable warnings. Visual QA and execution of checks belong to the main task. ## Numeric screenshot review policy

OCR means optical character recognition: converting screenshot pixels into text. Tesseract can return granular word and symbol information through its `blocks` output; the app now requests this for health, AP and countdown reads, while identity reads do not request or act on confidence. See the first-party [recognize API](https://github.com/naptha/tesseract.js/blob/master/docs/api.md#worker-recognize) and [result types](https://github.com/naptha/tesseract.js/blob/master/src/index.d.ts).

The implemented rule is a soft review hint when any recognized digit has a confidence score below 75. If symbol detail is absent, only a purely numeric word's confidence is considered. Unit words, letters and punctuation do not trigger warnings. The threshold is an initial product heuristic, not a calibrated accuracy probability or a guarantee of catching every wrong digit. High confidence can still accompany an incorrect reading. Missing/unparseable numbers retain their existing errors. Low confidence never independently prevents saving a valid reading, and no confidence warnings are shown for titles or mushroom types. [Policy and threshold](../src/screenshotConfidence.ts), [read integration](../src/readBattleScreenshot.ts), [policy tests](../src/screenshotConfidence.test.ts), [numeric-versus-name regression](../src/readBattleScreenshot.test.ts).

The ticket rename is presentation-only: existing `usesFreeTry: false` data still excludes a mushroom ticket from the free daily allowance. The shared helper beneath sleep and minimum-time settings says “Flags potential misses when there’s too little awake time to reach the next mushroom task,” matching the existing task-transition calculation; no sleep markers or extra allocation rules were added.
